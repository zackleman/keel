§01

What this is

Keel (upstream: Kevin’s kcosr/keel, MIT) is a durable agent-workflow orchestrator. A workflow is an ordinary async (ctx, input) => output TypeScript function. Every external effect — an LLM agent call, a shell command, a timer, a human approval — goes through ctx.* and is journaled to a SQLite-WAL store owned by a single-writer daemon. If the process dies at minute 105 of a 106-minute run, resume re-runs the function: the 104 completed effects replay instantly from the journal and only the interrupted one runs again. Edit the code and relaunch, and content-addressed versioning re-executes only the steps your edit actually invalidated.

That kernel is upstream keel, unchanged. Our fork — the onyx-extensions branch — ports in the capabilities we admired in the Onyx/Slate orchestration VM, whose confessed open problem (durability) is keel’s solved core. Concretely, we added:

§02

Mental model — three planes

Keel is easiest to hold as three planes that meet at one journal. The workflow body never touches the outside world directly — not the filesystem, not the network, not even the clock. Every side effect is a journaled effect that crosses a plane boundary as JSON.

plane 1 · inside the realm

Authoring

The ctx API, and nothing else. The body runs in a confined Bun Worker realm: JSON in, JSON out, no ambient fs/net/clock/random — a static lint rejects Date.now(), Math.random(), fetch, and friends before launch; the sealed ctx is the only escape hatch.

ctx.now() and ctx.random() are the only time and entropy sources, and both are journaled. Plain code between ctx.* calls (loops, reducers, dedupe) is not journaled — it just re-runs cheaply on every resume.

DESIGN.md §6 · USAGE.md “Determinism Rules”
plane 2 · the daemon

Execution

A single-writer daemon owns everything durable: the SQLite-WAL journal at ~/.keel/keel.db, the artifact store, timers and scheduling, the realm host, and agent subprocesses. The daemon — never a client — spawns agents.

Every effect follows the write-ahead lifecycle (§04): commit a pending row, execute, then transactionally commit the completed result. Resume is just re-running the function with a memoizing ctx.

DESIGN.md §5, §7
plane 3 · from outside

Supervision

CLI, TUI, web, and — new in this fork — an MCP server are thin clients over one RPC gateway and one canonical RunProjection. No surface rebuilds journal state; humans and agents read literally the same projection.

Supervisors watch progress (tail_checkpoints), read live state (get_state), steer (send_signal → ctx.drainSignals), decide approvals, interrupt and resume — without ever touching the database.

docs/mcp.md · docs/control-surfaces.md
The seam that makes steering safe: a steer message doesn’t mutate a running prompt from the outside. It sits durably in a per-run FIFO until the workflow chooses to drain it and compose it into the next agent turn’s prompt — so the steer content flows into that effect’s identity hash like any other input, and replay stays exact.
§03

Architecture

One daemon owns everything durable. Clients — including the authoring agent that wrote the workflow, and the supervisor agent watching it — talk to the daemon over a unix-socket RPC and never touch the database. The workflow body runs in a confined realm worker and reaches the world only through journaled effects.

§04

Data flow — how durability actually works

Every effect in keel is identified by three values, and everything else follows from this triple:

stableKey — author-chosen identity, content-derived for fan-out (never an array index) inputHash — SHA-256 of the inputs; upstream results contribute their content hash version — structural hash of the step definition (schema + resolved spec + capabilities)

An effect whose triple matches a completed journal row replays its recorded result and never runs again. A changed triple executes fresh as a new attempt, and the old row stays as auditable history. Here is one effect crossing the write-ahead protocol:

What replay means in practice

crash mid-effect

kill −9 at minute 105

On restart the daemon rebuilds all run state from the journal (a CAS fence on runtimeOwnerId stops a stale daemon from double-driving). Completed rows replay exactly once; the one pending row re-executes. The chaos harness proved it: the interrupted provider call ran twice, the journal recorded one completed attempt, and the checkpoint timeline had zero duplicates.

resume

Re-run, don’t restore

There is no separate replayer. Resume re-runs the whole function with a memoizing ctx: journaled calls short-circuit, plain code between them recomputes in milliseconds. Parked runs — waiting-timer, waiting-human, waiting-signal — cost nothing while parked and survive reboots; signals queued while the daemon was down are drained FIFO on resume.

edit + relaunch

Suffix-only re-execution

A rerun with a source override snapshots a new immutable definition. Structural per-step versioning plus value hashing invalidate only what changed — with early cutoff: if an edited step reproduces byte-identical output, everything downstream still replays. Chaos item 4: editing the last iteration’s prompt re-ran exactly experiment:2 and nothing else.

Why ctx.state reads are free — the replay trick NEW

The crux of ctx.state was choosing what to journal. Journaling every read (Option A) matches the existing machinery but poisons loops: an edit that inserts one read shifts every later occurrence onto the wrong recorded value — silent corruption, keel’s worst failure class. So only writes are journaled effects (Option B), with the written value folded into the effect’s own identity. A read is a synchronous, zero-cost fold over the writes that preceded it in this execution pass — correct by construction for run-scoped, single-writer state, because writes replay deterministically in program order. The daemon also materializes a state table (schema v23) in the same commit transaction, so supervisors get O(1) reads over MCP; it is a rebuildable cache the journal can always reconstruct — rewind deletes it, replay heals it.

signals

Durable per-run FIFO queues

Signals are named, durable, per-run FIFO queues. ctx.signal(name) parks and consumes the next one; ctx.drainSignals(key, name) NEW batch-consumes everything currently pending — without parking — and the consumption marks commit in the same transaction as the recorded batch. Rule of thumb: give a name to one consumer style, not both.

events

Append-only, cursor-resumable

Durable events carry a per-run monotonic seq. Clients resume with after-seq cursors and can reconnect days later without gaps or duplicates — the property the MCP tail_checkpoints/tail_events tools lean on. Live token deltas are ephemeral frames, deliberately not journaled.

§05

Worked example — autoresearch

This is real code — workflows/autoresearch/autoresearch.workflow.ts, the saved workflow the chaos matrix was run against (schema parsers elided for space, logic untouched). A setup agent proposes a hypothesis; an experiment loop drains supervisor steers, runs a typed agent per iteration, keeps or reverts by score in plain code, and checkpoints; a recorder summarizes; an optional human gate ships. Orange tokens are fork-added primitives.

workflow side — what the author wrote
import { type Ctx, type HumanDecision, jsonSchema } from "@kcosr/keel";

// Input / SetupResult / ExperimentResult / RecorderResult / HistorySchema:
// jsonSchema<T> parsers — their structural hashes enter effect identity. (elided)

export default async function autoresearch(ctx: Ctx, rawInput: unknown) {
  const input = Input.parse(rawInput);
  ctx.phase("Setup");
  const setup = await ctx.agent({1
    key: "setup", provider: "mock",
    prompt: "Establish a deterministic baseline and one testable optimization hypothesis.",
    schema: SetupResult, toolPolicy: "none",
  });

  const research = ctx.state<{ best: Candidate; history: HistoryEntry[] }>("research", {2
    best: ExperimentResult, history: HistorySchema,
  });
  await research.set({ key: "state.best.init", name: "best",
    value: { score: setup.baselineScore, candidate: "baseline", summary: setup.hypothesis } });
  await research.set({ key: "state.history.init", name: "history", value: [] });

  ctx.phase("Experiment");
  for (let i = 0; i < input.iterations; i++) {
    const steers = await ctx.drainSignals<Steer>(ctx.stepKey("steer", String(i)), "steer");3
    const best = research.get("best")!;  // synchronous fold read — free
    const lateInstruction =
      i === input.iterations - 1 ? "validate the final candidate" : "explore a candidate";
    const result = await ctx.agent({
      key: ctx.stepKey("experiment", String(i)), provider: "mock",
      prompt: [4
        `Iteration ${i}: ${lateInstruction}.`,
        `Hypothesis: ${setup.hypothesis}`,
        `Current best: ${JSON.stringify(best)}`,
        `Supervisor steers: ${JSON.stringify(steers)}`,
      ].join("\n"),
      schema: ExperimentResult, toolPolicy: "none", onFailure: "null", maxRetries: 0,
    });

    const accepted = result !== null && result.score > best.score;
    if (accepted) {
      await research.set({ key: ctx.stepKey("state.best", String(i)), name: "best", value: result });
    }
    await research.set({
      key: ctx.stepKey("state.history", String(i)), name: "history",
      value: [...research.get("history")!, { iteration: i, accepted, result, steers }],
    });

    await ctx.checkpoint({5
      key: ctx.stepKey("checkpoint", String(i)),
      message: `iteration ${i}: ${accepted ? "kept" : "reverted"}`,
      data: { iteration: i, accepted, best: research.get("best")!, result, steers },
    });

    if (i < input.iterations - 1 && input.cooldownMs > 0) {
      await ctx.sleep(ctx.stepKey("cooldown", String(i)), input.cooldownMs);6
    }
  }

  const { best, history } = research.snapshot();
  ctx.phase("Record");
  const recorder = await ctx.agent({ key: "recorder", provider: "mock",
    prompt: `Record the experiment history and winning candidate.\n${JSON.stringify({ best, history })}`,
    schema: RecorderResult, toolPolicy: "none" });
  await ctx.checkpoint({ key: "checkpoint.final", message: recorder.summary,
    data: { best, iterations: history.length } });

  let approval: HumanDecision | null = null;
  if (input.requireApproval) {
    ctx.phase("Ship");
    approval = await ctx.human({ key: "ship",7
      prompt: `Ship candidate ${best.candidate} at score ${best.score}?` });
  }
  return { best, history, recorder, approval };
}
annotations
1Keyed, schema-validated agent effect. Identity = key + resolved prompt + structural schema hash. Once completed, it never re-runs on resume — this is the atom of durability.
2ctx.state (new). The handle is pure; each set is a strict journaled effect with the value in its identity, so a stale value can never silently replay. Reads cost nothing. Supervisors see the same values live via MCP get_state.
3ctx.drainSignals (new). Consumes every pending steer signal FIFO, without parking; returns [] when quiet. In the chaos run, two steers queued while the daemon was down arrived in order at the next iteration.
4The steering seam. Steers and state compose into the prompt, so they enter the turn’s inputHash. External steering changes effect identity only through content the author chose to include — replay stays exact, no host-side prompt mutation.
5ctx.checkpoint (new). Durable progress: one checkpoint event committed in the same transaction as the completed row. Replay emits nothing — the timeline can’t double up.
6Durable park. waiting-timer costs nothing and survives restarts — chaos item 2 restarted the daemon after the deadline and the run woke correctly.
7Human gate. Parks waiting-human until an approval arrives — here, from the supervisor over MCP: decide_approval(…, "approved", "ship it").

Delivery semantics, stated honestly: send_signal acknowledges durability and wake-start — not that the worker saw the message. A steer sent mid-turn lands at the next turn boundary (Tier-1 contract); the supervisor observes uptake in the next checkpoint, exactly as above. If the MCP client restarts, it resumes from its persisted nextCursor with no gaps and no duplicates (chaos item 6).

§07

Governance & trust — untrusted code, trusted submitter

The deployment target is deliberately narrow: one daemon, one box — possibly remote, never multi-machine. Agents author workflow code; the operator’s own client submits it. So the adversary is not the client — it is the workflow source running inside the realm, which will try to shed whatever restrictions it was launched under. The submitter is trusted; the code is not.

ceilings · new

effective = min(declared, ceiling)

Workflow code self-declares its capabilities (tool policy, fs, shell, network, secrets). A submitter token carries a named ceiling profile (e.g. untrusted-default) that the daemon snapshots into the run at launch. A declaration above the ceiling fails closed at launch with capability_ceiling_exceeded — never a silent downgrade, which would change effect identity behind the author’s back.

The ceiling is re-asserted at runtime on every boundary: agent, agent session, command, completion check, and workspace-setup commands — five call sites in realm-host.ts.

escalation · new

Code requests; authority grants

A workflow that needs more than its ceiling doesn’t fail — it parks: ctx.human({ requestedCaps }). A supervisor reviews over MCP and answers decide_approval(…, grantedCaps). The grant is durable approval data, journaled with the decision, and may exceed the ceiling — that is the point.

Authority propagates with lineage, not by accident: spawned children copy the parent’s current snapshot at spawn time, continueAsNew successors and forks carry it too — the three escape routes a hostile workflow would try (§08).

promotion · new

Review-gated registry

One-off runs are ephemeral (opt-in GC after a TTL). Long-lived flows get promoted to the saved registry — and when any submitter credential is configured, every promotion requires an approved dedicated review: gate whose run executed the exact definition hash being promoted. A workflow’s own ship gate cannot satisfy it; source that never ran cannot skip it. Registry entries are immutable: name@version → definition hash, so a flow that runs unchanged for weeks is tamper-proof by construction.

What is deliberately not defended

The box is the boundary — stated plainly. Socket access is admin-equivalent, full trust: anyone who can reach the daemon’s unix socket can do anything, so the daemon is never network-exposed (ingress is Tailscale/SSH to the box). A run that has been granted write/command capabilities acts as the daemon user on that box. Provider tool flags are policy, not an OS jail; the network capability is advisory until a host-level egress firewall backs it. Keel’s realm confines the workflow body; granted effects run with real authority. Hence the ops posture in docs/deployment-hardening.md: dedicated non-privileged user, disposable volume, only the credentials the box needs, egress allowlist, rebuildable “cattle” VM. Per-agent bubblewrap/Landlock remains future defense-in-depth, not a current guarantee.
§08

Evidence

Durability claims are cheap; here is what was actually done to this system. The autoresearch workload ran as a saved workflow under a deterministic scripted provider (durability exercised for free, zero model tokens), supervised by a real keel mcp stdio process — and every item of the chaos matrix passed (docs/designs/workload-test-results.md).

1 · SIGKILL mid-turnPASS

Daemon killed while experiment:1 was pending. Restart: completed prefix replayed, the pending provider call re-executed (at-least-once), journal recorded one completed attempt, checkpoint timeline duplicate-free.

2 · delayed restartPASS

Killed at waiting-timer; two steer signals inserted durably while no daemon existed; restart delayed past the deadline. Both steers arrived FIFO in the next iteration’s drain.

3 · MCP steer mid-runPASS

Real stdio MCP client sent send_signal while a turn was in flight. “focus on parser” appeared in the next turn’s prompt and in that iteration’s checkpoint payload.

4 · edit + rerun overridePASS

Only the final iteration’s prompt changed → re-executed suffix was exactly experiment:2; its byte-identical output triggered early cutoff and the recorder replayed untouched.

5 · approval parkPASS

Run parked waiting_human; MCP decide_approval(…, "approved", "ship it") completed the run with the decision journaled.

6 · cursor resumePASS

MCP client read two checkpoint frames, persisted nextCursor, died. A fresh process resumed from the cursor: union = all four frames, monotonic seqs, zero overlap.

One phrase needed precision: a pending external effect is at-least-once, so the SIGKILL’d provider invocation genuinely ran twice. “No duplicate agent turns” means no duplicate completed journal attempt or durable event — a literal single-invocation guarantee would contradict the crash model, and keel does not pretend otherwise.

What the adversarial review caught — and what we hardened

Before merge, an adversarial review of the full diff (15 commits, 82 files) verified every finding against source: 3 critical · 7 major · 11 minor (docs/reviews/onyx-extensions-review.md). Its headline: the replay kernel work was sound, but the first cut of the Phase-8 ceiling model had three full-bypass routes — all of them the “code sheds its ceiling” attack the model exists to stop:
